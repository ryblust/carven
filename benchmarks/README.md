# Benchmarks

Build Carven before running benchmarks:

```shell
./xmakew build
./xmakew bench compile
./xmakew bench incremental
./xmakew bench simd
```

Windows uses `.\xmakew.ps1` with the same arguments.

| Topic | Measurement |
| --- | --- |
| `compile` | Fresh compiler processes over generated source workloads |
| `incremental` | Builds after source edits in a library, facade and application |
| `simd` | Carven byte-set scans and optimized C++ byte loops |
| `json` | Standard JSON byte validation on API-shaped documents |
| `async` | Generated async programs, C++ tasks and Carven runtime composition |

Runtime and incremental workloads are ordinary targets in the main project.
They use its built compiler, repository Carven rule and native toolchain.
The benchmark task builds the selected targets and measures them. Compiler and
native toolchain selection belong to the project's Xmake configuration.

Runtime targets use C++20 and explicit optimization settings. `--portable`
selects separate SIMD or JSON targets. Async targets have timing, allocation,
and stack profiles. Configure an optional libcoro checkout with
`./xmakew f --libcoro=/path/to/libcoro` before building.

| Option | Meaning | Default |
| --- | --- | --- |
| `--samples=<count>` | Number of measured runs | 3 for compile/incremental; 7 for runtime topics |
| `--warmups=<count>` | Number of warmup runs | 1 |
| `--case=<id>` | Select one exact case | All cases |
| `--list` | List cases without building or measuring | Off |
| `--output=<path>` | Save metadata, raw observations and summaries | Fresh file under `build/benchmarks/<topic>/` |
| `--verbose` | Show individual observations | Off |
| `--timings` | Show Carven stage details for compile/incremental | Off |
| `--command=check\|compile` | Compiler boundary for compile workloads | `compile` |
| `--compiler=<path>` | Built executable for compile workloads | Current `carven` target output |

Options work before or after the topic. Long options with values use
`--key=value`; options that do not apply to a topic are rejected.

```shell
./xmakew bench compile --list
./xmakew bench compile --case=modules_16 --command=check --timings
./xmakew bench incremental --case=private_function_edit --samples=2 --warmups=0
./xmakew bench simd --case=prefix_field --portable
```

`compile` starts a fresh compiler process for each observation. `check` measures
complete semantic analysis, including compile-time execution. `compile` also
includes C++ generation and writes to a fresh output directory. Native compilation
and linking are outside both boundaries. Warmups do not retain semantic results
between processes.

`incremental` uses one target and writable source directory for all scenarios in
`benchmarks/incremental/workload/` under the configured build directory. Scenarios
cover no changes, identical content rewrites, private and public edits, and
module addition and removal.
Each sample restores its baseline as needed, applies the edit and builds the
same target. Setup, restoration, timestamp waits and executable validation are
outside the measured interval. The native build uses C++20 with optimization
disabled. Checked Craft scripts remain shared with the main project.

Incremental observations record semantic analysis, C++ generation, generated
artifact changes and changed native objects for the workload target. They also
record changes to the independent module and unchanged generated bytes whose
timestamps changed. The runner enables compiler stage timings through Xmake's
`--verbose`; `--timings` prints the observation nearest the wall-time median.
Craft queries execute on each build. Unchanged samples require no semantic
analysis, C++ generation, or native object changes.

Runtime topics validate results before timing and check checksums after execution.
They calibrate program-internal timing intervals to at least 20 ms, then take
shuffled, interleaved samples. Allocation and stack observations use separate
programs and are excluded from timing summaries. Detailed workload boundaries
are documented in each topic's directory.

Reports retain commands, captured streams, compiler and native configuration,
input hashes, workload source snapshots and raw observations. Inputs include the
root project declaration and its resolved package rules; native configuration
records cover only the selected targets. Workload executables,
generated C++ and objects remain in the main project's build directories.
Existing report names are rejected. Failed runs retain completed observations.

Compare results using the same machine, inputs, compiler configuration and
measurement boundary. Summaries contain valid measured runs, excluding warmups.
Missing observations remain missing. Timings have no performance pass/fail
threshold; these workloads establish their recorded behavior and locality.
