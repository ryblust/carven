# 示例打磨与标准库扩展实施计划

- **Status:** Draft
- **Implementation:** Not started
- **Scope:** 三个应用示例的打磨、文本与数值标准库、原生桥接、networking 的分阶段交付，以及与 carven-xmake-repo 的配合。

## 目标与本轮范围

以日志分析器、混音器和 TCP 收集器作为真实使用者，推动 Carven 的常用代码更自然、生成代码更经济、标准库更实用。这三个示例已经覆盖编译期 JSON、静态与原生 SIMD 共用计算逻辑、双向原生异步调用、超时与失败恢复、关闭收尾，以及贯穿三个程序的数据流。本轮延续现有语义分析、结构化执行、后端实现选择和 Xmake 构建边界。

下一轮的主体是 P0 和 P1：直接打磨示例，补齐小范围文本和数值 API，降低原生提供者声明的重复。P2 交付可复用的网络后端及宿主集成，并为静态 sqrt 和公开连接对象完成有边界的验证。动态 Operation 集合、动态 when_all 和公开 concept 体系保留为 P3 候选。

本计划协调交付顺序和验收，不取代各设计域的语义所有权。生成器优化归属 `compiler-optimization.md`；若资源类型或容器准入需要新增源契约，分别归入动态所有权或数据表示设计。成熟后的行为说明进入 `docs/` 和相应标准库 README。

## 设计原则

Read、Write、Take 表达使用意图；编译器根据类型与生命周期事实选择实现。用户将数据当作值使用，并不意味着每个只读观察都必须产生独立物理副本。需要独立可写状态、保留旧值或满足原生可观察行为时，复制仍然有意义。

内建 API 可以由编译器检查类型能力、推导结果与失败集合、选择运行时实现。API 的实用性不以用户能否写出其完整泛型函数体为前提。print 的多参数能力和 when_all 的组合能力已经采用这种分工；本轮不把公开 concept、参数包、参数化闭包或高阶回调契约作为标准库扩展的前置条件。

Vector 应依据具体操作所需的能力建立准入和诊断，例如复制、转移、重定位、销毁以及保留借用。它不应了解异步调度、启动或取消协议。不过，当前“元素不含借用或可调用存储”等限制也服务于所有权检查，放宽限制必须补齐相应分析，不能只删除类型名单。内部能力判断与公开 concept 语法是两个可独立交付的事项。

标准库负责稳定的 Carven API、失败分类和使用约束；原生后端负责平台调用。编译器只为确有需要的受检查操作增加有限支持。Lua 规则依据编译器清单和原生构建配置工作，不解析 `.cv` 的语言语义。

networking 的原生实现依赖 runtime 的 execution 接口；runtime 核心保持独立，不反向包含标准库网络实现。这样可以复用异步基础，同时保留后端与库之间的依赖方向。

## P1 文本与数值标准库

### TXT-01 借用游标与字节行处理

先把单个 redaction 工作负载写好，再提炼最小公共 API。分词游标返回借用原文的片段，并明确保留空字段和空分隔符失败；通过普通类、枚举和显式 next 调用使用。优先用调用者持有原文、游标只持有偏移的形式，减少返回片段与可变游标之间不必要的生命周期耦合。

字节行处理分成两层。对完整 `[u8]` 的扫描只返回边界；对分块输入的 framer 拥有尚未完成的字节，显式 feed 和 finish，完成后逐条产出记录。第一版可以通过具体的状态和返回枚举暴露，不要求回调、泛型 iterator 协议、`Vector<str>` 或 pipeline 语法。

LF、CRLF、空行、最终不完整记录和最大字节数都是独立政策。日志分析器与收集器采用各自配置；共享工具不能把“日志允许无最终换行”和“收集协议拒绝未完成帧”合并成一种默认行为。UTF-8 验证留在完整记录层，以支持跨块多字节字符和逐记录恢复。

**验收：**分词覆盖空文本、空字段、多字节分隔符、连续空格及 borrow 失效诊断；framer 覆盖任意拆块、CR 与 LF 分开到达、UTF-8 拆块、边界长度、超限和 finish 政策。借用游标先用最小源程序验证，若现有检查不接受安全关系，单独定位该关系；不扩大为全套序列语言扩展。

### MATH-01 建立自己的 math API

需要自己的 math 标准库，因为示例应通过稳定的 Carven 数值 API 表达计算，并获得一致的类型和边界说明。运行时继续复用成熟 C++ 数值实现；不自行重写 libm、超越函数或近似算法。

首版建议采用 `std::math.float32` 与 `std::math.float64` 两个具体模块，各自提供 abs、min、max、clamp、sqrt。模块名和下表是 Draft API，实施前定稿。这样可以先交付自然的命名函数，不依赖用户函数重载、任意 T 上的算术能力或 concept。若以后统一为同名入口，可采用编译器受检查的有限数值族，不必先开放完整重载和泛型约束体系。

| API | 首版建议契约 | 执行能力 |
| --- | --- | --- |
| abs | ±0 结果为 +0；无穷按绝对值处理；NaN 仍为 NaN | 用现有标量操作实现 const fn |
| min / max | 任一输入为 NaN 时返回 NaN；数值相等时保留第一个操作数，含零符号 | 用现有比较与分支实现 const fn；明确其契约，不宣称与所有原生 min/max 完全相同 |
| clamp | 要求 `lower <= upper`，无序或倒置边界按 assert 契约拒绝；有效边界下 NaN 输入保留为 NaN | const fn；参数错误采用前置条件，不增加新的组合失败集合 |
| sqrt | 非负有限值按对应精度开方；+∞ 保持；负非零值与 −∞ 得到 NaN；±0 保留符号 | 首版运行时原生实现；静态能力由 MATH-02 补齐 |

不保证不同浮点环境下的逐位一致、NaN payload 的跨平台一致或非默认舍入模式一致；与现有浮点和 SIMD 文档保持同一边界。整数 abs 的最小值溢出、整数 clamp 的推断规则、三角函数、向量矩阵和随机数不在首版中。

混音器先用 math 的 abs 与 sqrt，并独立验证 f64 energy 策略。clamp API 不应隐藏原始溢出检查；SIMD 裁剪可以暂时保留现有 select 表达式，避免为了复用一个名字而改变错误行为。

**验收：**两个精度覆盖普通值、±0、NaN、±∞、边界相等、非法 clamp 区间和负 sqrt。静态支持的函数同时有 const 与运行时测试；运行时 sqrt 在 C++20 消费者中验证。RMS 的验收给出数值容差与累加策略，现有应用链的输出变化必须有数值理由。

## P1 原生桥接与规则仓库

### BRIDGE-01 提供者契约与公开类型

将真实平台实现和声明样板分别处理。网络的轮询、部分读写、错误映射和取消收尾仍由原生后端完成；生成工具负责降低提供者原型、失败类型拼写和头文件依赖的重复。

当前 import(cpp) 允许 C++ 在调用处选择重载和模板，并不生成或比较提供者声明。新方案采用显式启用的提供者契约产物：仅对选择的、具体签名的提供者生成规范原型，并为边界需要的 Carven nominal 类型与失败类型生成稳定可命名的公开别名。启用入口先选择 CLI 或构建选项，避免为此增加一套语言泛型功能。

类型别名仍指向同一个语义类型，不复制一套“桥接版本”的定义，也不改变私有字段权限。公开头文件只发布边界允许暴露的类型和依赖；稳定名称承诺属于 C++ 源码接口，不顺带承诺跨编译器二进制 ABI。

推荐把类型定义依赖与提供者声明分离：类型头可以被提供者契约头引用，API 头和实现按依赖顺序使用。具体拆分须以当前 generation plan 的依赖图为依据，避免 API 头、native.hpp 和 provider 原型循环包含。C++ 提供者包含契约头并定义函数；源码只保留一次 import 签名，不再用错误工厂的 decltype 或手写第二份原型获取类型。

**实施前关闭：**选择哪些 import 进入契约、公开类型命名与冲突规则、完整类型依赖、失败 carrier 的可见性及头文件包含顺序。旧的任意 C++ 适配模式继续按原契约工作，不能通过全局自动声明改变其重载集合。

**验收：**同步和异步提供者、void 结果、多种失败载荷、跨模块标准库类型，以及两个独立 C++ translation unit。契约头须能在声明所要求的依赖环境下独立编译；签名不符由规范声明或使用产生 C++ 诊断。收集器的手写原型和 decltype 样板可移除，实际资源关闭逻辑完整保留。

math 和 networking 可以先参考 `std::io` 的原生中立结果方式：native result 承载错误码和数据，Carven 包装映射到源失败类型。因此 BRIDGE-01 只约束消费其生成契约的边界，不阻塞全部标准库工作。

### BUILD-01 两个仓库的责任

| 事项 | carven | carven-xmake-repo |
| --- | --- | --- |
| 源语义与类型能力 | 检查访问、借用、失败、静态执行；发布后端事实 | 消费编译器结果 |
| 生成产物 | 生成完整清单、规范路径、来源归属和头文件依赖 | 在 native 扫描前完成生成，验证清单并发布产物 |
| 标准库文件 | 在 `crafts/carven` 交付 `.cv`、原生 `.cpp/.hpp` 和 README | 从安装与项目 Crafts 收集 `.cv/.cpp`，配置共享 library producer |
| 原生配置 | 定义必要平台条件、头文件要求与系统链接依赖 | 将构建要求应用到 producer 和消费者，维护正确的共享身份 |
| 安装 | 交付编译器、runtime 和完整 Crafts 树 | 完整包安装及 rules_only 模式接入 |
| 验证 | 语义、执行、桥接、示例链及生成清单测试 | 用真实消费项目验证配置、依赖、增量和共享 |

新增标准库目录通常利用已有 inventory 即可收集，不为 math 或 networking 在规则里硬编码函数名。新增契约头进入编译器清单；若只新增头文件，沿用现有发布机制。若新增生成 `.cpp` 或改变稳定的 module-to-implementation 路径，须同步修改注册和清单验证契约，避免 native 扫描看到未注册实现。

网络系统依赖归属包或明确的标准库构建需求。首版建议在规则的标准库 native 配置入口统一加入 Windows `ws2_32` 等实际需要的平台配置，完整包和 rules_only 共用该入口，并显式把系统链接要求应用到消费者；包与规则文档记录对应要求。这样先移除示例中的重复配置，后续存在更多平台依赖时再提炼 Crafts 元数据。要求必须同时满足网络原生 producer 的编译和最终消费者的链接；当前共享 producer 使用不继承依赖输出的接入方式，不能假设系统库会自动传到可执行文件。不要因一项系统依赖先引入通用第三方包 DSL。

现有共享身份依据 compiler、Crafts 位置、工具链、有效 native 编译设置和 prerequisites 等事实建立。新增浮点策略或网络功能宏必须在共享选择前进入有效配置；只在链接时使用的要求也须正确传到消费者。相同配置复用一份 producer，不同有效编译配置不得误共享。

安装验收同时覆盖本地 rules_only 与完整 package。测试应包含新增文件后重新配置、安装树更新、无操作重建、公共头变化、私有实现变化、删除旧产物，以及编译器失败不发布新一轮产物。现有 staging 发布不构成多文件事务承诺，本轮不扩大为新的构建事务系统。

## P2 网络能力与有限执行扩展

### NET-01 复用 TCP 后端与宿主集成

先把示例里的平台 socket 操作、事件注册、NativeAwaiter、错误码和取消收尾迁入 `crafts/carven/std/net` 的原生实现。应用保留自己的收集协议、Feed 状态、超时和恢复政策；7 字节读块与 5 字节写块这类人为拆分转入测试注入，通用 API 不固定这种分块。

第一步继续使用宿主持有的连接资源和显式 EventSource。提供具体的 read 与 write 包装，返回普通冷 Operation；读结果复用 `Read<Vector<u8>>` 的 Data/End 形式，写结果表示已完成字节数，write_all 由已有循环与 await 组合。建议使用具体的 NetError，至少区分系统错误码、已关闭连接、操作冲突和无进展写入；原生中立结果在 Carven 中映射，不把正常 EOF 当作错误。

首版 read 要求请求上限大于零，使用前置条件拒绝零上限；Data 至少包含一个字节，End 表示对端正常结束发送。write 的空输入成功返回零，非空输入允许短写；write_all 的非空剩余数据遇到零进展时失败，不能忙循环。同一连接允许同时有一个读和一个写，重复的同方向活动操作报告冲突；取消沿用核心的独立完成状态，不伪装成 NetError。

网络 read 不承诺一条业务记录。以当前同线程 driver 接口组合网络、计时和已有 I/O 事件，避免为了 socket 引入第二套异步调度器。超时后的 close 要等 provider 不再能访问状态，再释放 socket 和缓冲。POSIX 优先采用 socket 或发送调用级的 SIGPIPE 抑制；不让库初始化静默修改整个进程的信号政策。Windows 初始化和清理归属明确的宿主适配器生命周期。

宿主集成版本仍有明确的 native 生命周期义务：source 的 context holder 检查无法证明其内部 fd 或 callback 生命周期。将这一义务收敛到一个可复用适配器和接入文档，不能把隐藏原生指针包装成看似自动安全的 source 所有者。

**验收：**loopback 的部分读写、多字节 UTF-8 拆块、EOF、失败、背压、超时与取消；连接和事件注册只释放一次，关闭后无回调访问。至少用两个消费者验证复用，而非只把示例文件搬目录。已有应用链仍能运行。Windows 和 POSIX 的初始化、关闭与发送错误政策由各自适配器明确管理。

### MATH-02 静态 sqrt 与 SIMD 辅助

在 MATH-01 契约稳定后，为两个具体精度的 sqrt 增加共享语义操作，使静态执行使用编译器宿主计算，运行时仍降低到对应原生计算。不能因某个 C++ 函数带 constexpr 就自动把它当作 Carven 静态操作，也不能给包含未获准 native call 的函数直接加 const fn。

操作身份依据标准库 canonical declaration 或已建立的 builtin 发布路径，不按用户函数名字猜测。明确特殊值、执行模式、预算和精度边界，补齐语义检查、结构化执行、解释路径中适用的实现以及后端 lowering。该项属于有限内建执行能力扩展，不要求新语法或公开 concept。

SIMD 只先补示例确有用途的 concrete helper，例如有明确 NaN 政策的 abs 或 clip。保留原始非有限值检查的位置。浮点水平归约必须先选择顺序、误差与是否允许重排；本轮没有测量收益和契约前维持逐 lane 累加，不以新增 API 数量作为完成标准。

**验收：**相同标量程序可在 const 与运行时计算 RMS；特殊值遵循共同契约，普通结果按精度容差比较。SIMD helper 与标量逐 lane 基准对照，含尾部 mask。性能结果分别记录内核、整个示例、生成代码与原生编译成本。

### NET-02 公开连接 API

下一步目标是源程序能自然表达连接、读写和关闭，而无需每个项目重建 provider。地址首版限于字面 IP 与端口；先选定需要连接、监听或接受中的具体使用场景。DNS、TLS、HTTP、跨线程 reactor 与完整生产级协议栈各有独立资源和失败契约，等待真实消费者。

资源设计先区分“宿主持有连接的借用视图”和“source 拥有连接的 Stream”。前者可以延续 NET-01 的显式宿主合同；后者须禁止意外复制 socket 所有权，规定转移、销毁、未启动 Operation、活动借用与关闭后的访问。普通 value class 不能凭名称自动获得这些保证。

优先用现有 native RAII 与具体包装实现，但不能让 C++ 编译失败成为唯一的 source 所有权说明。如果现有类型事实无法表达 noncopyable 所有者或其借用关系，可以增加受检查的有限资源类型及其能力传播；这属于真实的源契约扩展，单独记录并验证。它不要求先实现通用 Unique、用户自定义析构钩子或 concept。

**本轮关闭条件：**用一个最小 TCP 用例确定需要的所有者与借用视图，写出创建、转移、挂起、取消、关闭和销毁状态，逐项映射现有检查。能映射的部分进入实现；缺失的源规则先形成独立设计。NET-01 的可复用后端仍可独立完成。

## P3 容器与动态组合候选

### VEC-01 Vector 的类型能力

当前 runtime Vector 的扩容和 push 已经使用转移，但复制构造、复制赋值以及 from_slice 仍以元素可复制为前提。Operation 在原生运行时不能复制、可以转移；其源值还可能保留参数借用。因此支持 `Vector<Operation<...>>` 需要检查运行时方法、source 的 Vector 能力推导、元素借用关系传播、取出与访问、销毁及静态执行准入，不能只放开类型形成。

未来可在编译器内部建立按操作检查的能力表：有复制能力时允许 Vector 复制；有重定位能力时允许扩容；完整转移 Vector 所有者不等同于复制元素；复制构造来源与转移来源分别检查。Operation 的启动、完成和取消仍属于异步组合，Vector 只负责存储、访问和生命周期。原生类型、借用类型和可调用值也各有独立边界，不因一个 Operation 案例一次全部放开。

这里反映的是保守的容器准入政策，以及 move-only 元素和相关借用检查尚未完整覆盖，不能据此断言基础泛型架构有根本缺失。容器实现及有限类型准入可以独立完善，公开行为的放宽也需要更新语言契约，但不自然推导出必须拥有用户可定义的 concept。现阶段不实施；出现独立于动态 when_all 的真实 move-only 容器消费者，或现有编排产生明确成本时重新启用。

### ASYNC-01 有限动态 when_all

运行时数量的输入在 API 外形上可以很简单：消耗同一结果和失败类型的 Operation 序列，返回按输入顺序排列的结果序列。编译器受检查的入口可处理类型与失败集合，不需要高阶回调或越来越深的公开 tuple 类型。

简单外形仍要求固定活动子任务状态的地址、启动失败后的清理、取消后等待全部 provider 收尾，以及携带借用的检查。实现时可以先分配固定数量的槽位再启动，不需要扩展成可随时增删任务的 supervisor。只有有限动态 when_all 消费者出现时，才与 VEC-01 一起重新评估具体范围。

对外结果及其后备存储必须在其余输入的取消和收尾期间保持有效。结果序列须满足元素构造与转移要求；已存入完成槽的不可移动结果，需要最终位置构造或拥有后备存储的交付契约，转移完成句柄本身不会转移载荷。

状态和分发按运行时槽位组织，不枚举剩余输入子集或完成排列。验证行为时分别测量栈、状态分配、分发和生成代码规模。现有顺序 await、固定批次 when_all 和普通 async 包装作为比较基线。

### LANG-01 公开泛型能力

concept 等设计按现有 `generic-extensions.md` 的边界推进，不因本轮标准库工作提前扩大范围。重新启用条件是用户需要定义自己的可复用能力约束、参数化高阶接口或开放扩展点，并且有限内建 API 已无法自然服务具体用例。内建是否方便，与公开泛型是否需要扩展分别评价。

完整包另用 `CARVEN_SOURCE_DIR=/Users/rybel/dev/carven` 安装到隔离消费项目，验证安装树内的新标准库、头文件和平台依赖。现有 incremental workload 用于回归；新的生成头与网络配置场景应扩展真实消费 fixture，不能假设一个私有编辑 case 覆盖所有配合项。遇到异常 BMI、依赖顺序或不可能的类型错误，按项目约定先 clean、build 并复现，再诊断实现。
